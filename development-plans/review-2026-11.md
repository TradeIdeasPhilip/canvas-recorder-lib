## Export bit rate

The recording is HEVC at 16 Mbps ([dev/canvas-recorder.ts:1171-1177](../dev/canvas-recorder.ts#L1171-L1177)).
That's modest for 4K at 60 fps, and the file is the master that YouTube re-encodes, so a higher rate only costs file size.
Line art compresses very well, so 16 may be plenty.

**Try:** next time a video is ready, save one short, busy section at 16 Mbps and again at 40 Mbps.
Change nothing else. Compare them on screen, and after YouTube. Keep whichever is better; if they look the same, keep 16.

## `save()`/`restore()` around every child

**The idea:** every container wraps each child's `show()` in `context.save()` … `context.restore()`.
Then a component can change anything about the canvas state, and nothing leaks into its siblings.
The canvas state rules in CLAUDE.md shrink to one: start every path with `beginPath()`, because the current path isn't part of the saved state.

**Measured 2026-11-03,** Chrome for Testing 1243 on this Mac, a 3840 × 2160 canvas:

| What                                        | Cost                             |
| ------------------------------------------- | -------------------------------- |
| One `save()` + `restore()` pair             | about 190 ns                     |
| The same, with a `translate()` between them | about 230–255 ns                 |
| 1,000 pairs per frame                       | about 0.2 ms, of a 16.7 ms frame |
| Stroking 100 small paths, for comparison    | 12–17 ms per frame               |

With strokes in the frame, wrapping each one in `save()`/`restore()` made no difference bigger than the noise between runs.
A `clip()` inside didn't either.
Method: 60 frames each, `getImageData(0, 0, 1, 1)` at the end of each frame so the GPU work is counted, and the same drawing with the transform undone by hand instead, for comparison.

So the cost is nothing at the level of a component, or even a helper function.
Don't do it per point in a loop of thousands, but nobody does that.

**Where:** `InParallelComponent.showChild()` and `show()` ([src/slide-components/in-parallel.ts](../src/slide-components/in-parallel.ts)), which most containers inherit; `InSeriesComponent.showChild()`; and the transitions, which draw two children.
A parent's state still reaches the child, because `save()` copies it rather than resetting it. Only the child's changes stop leaking.
The only thing that could break is code that relies on a leak, like a "setup" child that sets `lineWidth` for the siblings after it. None is known.

## Glitch-free parametric paths

`PathBuilder.addParametricPath()` ([src/glib/path-shape.ts:1244](../src/glib/path-shape.ts#L1244)) and `PathShape.glitchFreeParametric()` ([:2156](../src/glib/path-shape.ts#L2156)).

**What it does:** sample the function at fixed `t = i / n`, with each sample's point and direction (by finite difference).
Each pair of neighbors becomes one quadratic Bézier, whose control point is where the two tangent lines cross (`Q_angles()`, [:1121](../src/glib/path-shape.ts#L1121)).
Then the glitch-free layer finds segments much longer than the straight line between their ends (more than 2×), and redraws those stretches with more segments, up to 4 levels deep, with a straight line as the last resort.

**Why each frame is consistent with the next:** the samples are at fixed values of `t`.
When the function changes a little, every sample moves a little, so the whole drawing moves a little.
Nothing ever decides how many pieces a part of the curve needs, so nothing can pop from one frame to the next.
A loop that shrinks to nothing is just samples getting closer together; the sampler never notices there was a loop.
Adaptive methods, which add points where the curve is complicated, are better for one still picture, and worse for animation for exactly this reason.
Choosing the segment count from the highest frequency, `8 * maxFrequency + 7` in [fourier-shared.ts:434](../src/peano-fourier/fourier-shared.ts#L434), is about 8 samples per turn of the fastest circle: a sensible rule.

**Where the glitches come from:** the tangent-crossing control point is the weak spot of the one-control-point quadratic.
When the two tangents are nearly parallel, they cross far away, or behind; that happens across an inflection (an S bend) and on nearly straight stretches.
That's the long, thin parabola the glitch layer catches. It treats the symptom well.

**An idea, if it's ever worth a try: cubic Béziers from the same samples.**
With each sample's velocity (direction _and_ speed, which the finite difference already has), the segment from `t₀` to `t₁` is exactly one cubic Bézier:
control points `P₀ + v₀·Δt/3` and `P₁ − v₁·Δt/3` (Hermite to Bézier).

- It's never infinite or behind, and one cubic can bend both ways, so an S bend needs no rescue.
- It's more accurate for the same number of segments.
- The glitch layer would almost never fire, so the segment count would stay fixed, which helps the frame-to-frame consistency too.
- Canvas draws cubics about as fast as quadratics, and `PathShape` already has `CCommand`.

The catch: code downstream may expect `Q` commands from these paths (`QCommand`'s requested angles, path morphing, splitting).
So it would be a new function next to the old one, e.g. `PathShape.hermiteParametric()`, tried on the Fourier slides, not a replacement.
For Fourier sums the derivative could even be exact, from the terms, instead of a finite difference.
